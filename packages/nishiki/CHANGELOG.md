# Changelog

## 0.1.0

The first release of nishiki as `@nishikijs/react`: atomic CSS-in-JS for React 19, with the `styled()` and `css` prop ergonomics of styled-components and an optional compiler. nishiki is a fork of [restyle](https://github.com/souporserious/restyle). It is experimental, so the API and the generated class names may still change.

- **Overrides that do not depend on load order.** Inputs merge per top-level key, the later winning, and every rule sits in a cascade layer ranked by its condition (media queries on a breakpoint ladder, then container queries, `@supports`, attributes and ancestors, and pseudo-classes) and by how much its property covers. A rule wins the same way whether it came from the runtime, an extracted stylesheet or both, whichever route the visitor arrived from. Rules nishiki cannot rank still tie and fall back to document order, such as two width queries the order does not list, which share a rank.
- **React Server Components.** Rules render as React 19 `<style href precedence>` elements, which React hoists and deduplicates, so `styled`, the `css` prop and `css()` work in Server Components with no `'use client'`, provider or style registry.
- **A compiler with a lean runtime.** The optional compiler, `@nishikijs/react/unplugin/<bundler>` for Vite, Rollup, Rolldown, webpack, Rspack, Rsbuild, esbuild, Bun, Farm, unloader and Next.js, compiles literal styles at build time with the same code as the runtime and hoists static styles out of render. Compiled client modules load `@nishikijs/react/lean`, which leaves out the condition ranker. Without the compiler, everything still works at runtime.
- **CSS split per route.** With `extract`, compiled rules move to static stylesheets: one per entry and lazily loaded chunk, with only the rules it adds, in Vite client builds, Rollup, Rolldown, and production client builds of webpack, Rspack, Rsbuild and Next.js with webpack. `extract: { split: "single" }` gives one stylesheet per entry.
- **Runtime values as CSS variables.** A dynamic property value on an element compiles to one static rule that reads a custom property the element sets inline, so new values add no CSS and no rule work at render. A value in a `css()` call, on a component the compiler cannot see render an element, under a selector or at-rule key, or that is an object, and a CSS-wide keyword or `!important`, keeps a rule of its own.
- **Compact class names.** With `extract: { classNames: "compact" }`, a build that plans its stylesheets names its rules `_0`, `_1`, … instead of hashes, for apps whose markup no other build renders.
- **Requirements.** React 19 and Node.js 24 or later.

Start with [Getting started](https://nishiki.ryoppippi.com/getting-started/), or [Migrating from styled-components](https://nishiki.ryoppippi.com/migrating-from-styled-components/) and [from restyle](https://nishiki.ryoppippi.com/migrating-from-restyle/).

The entries below record what changed while nishiki was developed as kiln, before this first release. They matter only to code written against those earlier builds.

### Breaking changes

- kiln is renamed to nishiki and published as `@nishikijs/react`. Replace the `kiln` dependency with `@nishikijs/react`, every import from `kiln` or `kiln/<entry>` with `@nishikijs/react` or `@nishikijs/react/<entry>` (`/core`, `/compiler`, `/lean`, `/jsx-runtime`, `/jsx-dev-runtime`, `/unplugin`, `/unplugin/<bundler>`, `/unplugin/loader`), and `jsxImportSource: "kiln"` with `jsxImportSource: "@nishikijs/react"`, in `tsconfig.json`, the framework's React plugin and any hand-written Turbopack rule. The plugin's default `importSource` is `@nishikijs/react`. Rollup and Rolldown builds with `extract` list their stylesheets in `.nishiki/manifest.json` (`.nishiki/manifest.<format>.json`) instead of `.kiln/manifest.json`, so update a page or server that reads it. Per-module CSS is named `<source>.nishiki.css` instead of `<source>.kiln.css`, the `<style>` precedence is `nishiki`, and warnings and errors start with `[nishiki]`. Class names and cascade layers now start with `n` instead of `k` (`n0`, `n1t.a.a`), so every class name changes; a stylesheet or test that names a class or layer must be updated. The installed skill moves to `skills/nishiki`.
- The compiler is now part of `kiln` instead of a separate `unplugin-kiln` package. Replace `unplugin-kiln` with `kiln/unplugin` and `unplugin-kiln/<bundler>` with `kiln/unplugin/<bundler>`, including the `unplugin-kiln/loader` path in a hand-written Turbopack rule with `kiln/unplugin/loader`, and remove `unplugin-kiln` from your dependencies. The compiler's dependencies are installed with `kiln`, and the runtime entries (`kiln`, `kiln/core`, `kiln/compiler`, `kiln/lean`, `kiln/jsx-runtime`, `kiln/jsx-dev-runtime`) never import them.
- Rollup and Rolldown builds with `extract` now plan and emit kiln's own stylesheets, as Vite client builds already do: one per entry and lazily loaded chunk that adds rules, with only the rules it adds. Modules no longer import a `<source>.kiln.css` module, so a CSS plugin that collected those modules receives nothing; remove it. Each chunk loads its stylesheet itself before its code runs, and `.kiln/manifest.json` lists the stylesheets that load with each chunk, so the page can link an entry's. `extract: { split: "single" }` gives each entry one stylesheet instead. Output formats other than ES modules get one stylesheet per entry, which the page must link from `.kiln/manifest.<format>.json`, such as `.kiln/manifest.cjs.json`.
- Production client builds of webpack, Rspack, Rsbuild and Next.js with webpack and `extract` now get kiln's planned stylesheets too: one sheet per entry and lazily loaded chunk group that adds rules, with only the rules it adds. Previously each source module's CSS was bundled per chunk, repeating shared rules in every stylesheet on the way. kiln adds the rules to the stylesheets the CSS pipeline already emits, so webpack's and Rspack's own CSS loading, HTML plugins and Next.js serve them. This needs a pipeline that emits stylesheets: mini-css-extract-plugin, Rspack's `CssExtractRspackPlugin` or native CSS. Such a build now fails when the pipeline keeps kiln's CSS in JavaScript anyway, as a rule of its own with `style-loader` would, or emits no stylesheet for a chunk that a sheet must go in. kiln's rules no longer pass through the pipeline's loaders, such as PostCSS or Rsbuild's Lightning CSS transform, though its minimiser still runs. This needs `optimization.realContentHash`, which is on by default in production; without it kiln warns and keeps a CSS module per source module. It also needs `[contenthash]` in every stylesheet's name, the only name `realContentHash` updates; where one has none, kiln warns and gives each stylesheet the rules of its own CSS modules. `extract: { split: "single" }` gives each entry one stylesheet, in a chunk that only it loads; where the pipeline emits no stylesheet for any such chunk, kiln warns and splits by chunk instead. Development builds, builds whose CSS pipeline emits no stylesheets (such as `style-loader`, css-loader's `exportOnlyLocals`, null-loader, or native CSS for a target without a document), server builds (with a target other than the web, Next.js's server builds or Rsbuild's non-web environments) and Next.js with Turbopack are unchanged.

- Rules under different conditions now win by the rank of their conditions rather than by their order in the document, so overrides land whatever order rules load in. Rules for one property under two overlapping media queries, `:hover` against `:focus`, or `.dark &` against `[data-state]`, used to share a layer and a specificity, so whichever the page had inserted later won: at runtime the order React first inserted them, which follows the page's history, and in extracted CSS the order of the sheets, where a sheet fetched again moved a rule. Media queries rank below container queries, `@supports`, attributes and ancestors, and pseudo-classes; width queries follow a breakpoint ladder, Tailwind's by default; pseudo-classes follow Tailwind CSS v4's variant order. A rule under two or more conditions ranks by the highest of them, above any rule under one, where it used to rank by nesting depth. Configure the ranks with the plugin's new `conditions` option or `configure()`. Conditions the order does not list share one rank per category and warn.
- Properties layer by how much they cover, from a table generated from the CSS specifications: `all` lowest, then broader shorthands below narrower ones, logical longhands below physical ones. The hand-written lists missed shorthands such as `insetInline`, `borderInlineWidth`, `scrollMarginBlock` and `containIntrinsicSize`, prefixed ones, `all`, and logical against physical longhands, which tied.
- `LAYER_ORDER` is replaced by `layerOrder()`, which returns the order of the configured layers. Layers are named by rank, with broader properties in nested layers (`k1t.a.a`), instead of `k0` to `k11`. `<Styles>` and the css prop insert it ahead of their rules, and React hoists it to the start of the head. If a template links extracted stylesheets before React's output in the head, render `<style>{layerOrder()}</style>` at the top of the head, before any extracted stylesheet.
- A selector list nested in a style, such as `{ ":hover": { "& span, & em": … } }`, compiles to one rule per selector, since each selector ranks on its own.
- Extracted stylesheets declare only the layers the build uses. A sheet kiln plans, with Vite, Rollup, Rolldown, webpack, Rspack, Rsbuild or Next.js, that always loads after another sheet leaves the statement out.
- Compiled modules import the runtime from `kiln/lean` in client builds, which leaves out the compiler that ranks conditions at runtime; a module that leaves a style object to runtime imports `kiln/compiler` as well. Compiled code calls a new `__v` helper for a property's runtime value, which the build ranks, so code compiled by an earlier version has to be compiled again. Compiled code ships what each rule is made from, its value and layer and, where they differ from the key, its property, selector and at-rules, and the runtime's `__k` helper formats the rules and their class names when the module loads; with `extract`, each entry is only its key and class names, which a new `__x` helper reads without the code that formats rules. Code compiled by an earlier version has to be compiled again for this too.
- Client builds load `@nishikijs/react/lean` for compiled modules with every bundler, now including Next.js with Turbopack and Bun, and with an `importSource` of your own that exports the lean entries. The compiler writes the lean entries into each module rather than having the bundler resolve them: it points the module's imports of `@nishikijs/react`, `/jsx-runtime` and `/jsx-dev-runtime` at their `/lean` counterparts and, with the `css` prop on, starts the module with a `/** @jsxImportSource @nishikijs/react/lean */` pragma, so it assumes the module's JSX compiles against `importSource`, as the `css` prop already did; a module's own pragma for another source is kept. Outside client builds, a module that leaves a style to the runtime no longer imports `@nishikijs/react/compiler`, since the full entries it loads include it. An `importSource` other than `@nishikijs/react` must export `/lean`, `/lean/jsx-runtime`, `/lean/jsx-dev-runtime` and `/compiler`, re-exporting nishiki's; without them the build warns and keeps its full entries, as every build with a custom `importSource` used to.
- `kiln`, `kiln/core`, `kiln/compiler`, `kiln/jsx-runtime` and `kiln/jsx-dev-runtime` are marked as having side effects: importing them loads the compiler into the runtime.
- `compileEntry` from `kiln/core` returns a list of entries, one per selector of a selector-list key, and keys each by its merge key (`"&:hover"` as `":hover"`).
- A key that a later input overrides now moves to where it was last set, so its rules come after the rules of keys it did not override. With a base of `{ "@media (min-width: 900px)": …, "@media (min-width: 600px)": … }` and an override of the 900px query, the override now beats the 600px query where both match, instead of losing to it. Class names come out in the new order too.
- Keys that select the same elements merge as one: `"&:hover"`, `" :hover"` and `":hover"` override each other instead of emitting rules that tie, and a selector-list key such as `":hover, :focus"` compiles to one rule per selector and merges per selector, so a later `":focus"` overrides only its part. Class names of selector-list keys change.
- Within one top-level key, only the last declaration of a property under one condition is emitted, so `{ "@media print": { ":hover": { color: "red" }, "&:hover": { color: "blue" } } }` gives one rule instead of two that tie. A bare `&` adds no condition, so in `{ "@media print": { "&": { color: "red" }, color: "blue" } }` the later `blue` applies.
- Every rule sits inside one top-level cascade layer, `nishiki`: `n0` is now `nishiki.n0` and `n1t.a.a` is `nishiki.n1t.a.a`, and the layer statement is `@layer nishiki{@layer n0,…;}`. Class names do not change. nishiki's layers used to sit at the top level beside the page's own, so a layer the page declared between two of nishiki's statements, such as a reset loaded after the first extracted sheet, ranked above some nishiki rules and below others, and the page could not order its layers against nishiki's without naming each of them. Now a page layer ranks above or below every nishiki rule, and `@layer reset, nishiki;` declared before nishiki's styles puts the reset below them. A stylesheet or test that names a nishiki layer must add the `nishiki.` prefix.

### Performance

- With `extract`, a `css` prop whose style is a literal object on an element such as `<div>` compiles to a `className` holding its class names, after the element's own. The element's `className` expression, if any, is joined with them through a new `__j` helper. A component, or an element with a spread, keeps the `css` prop.
- With `extract`, a `css()` call of nothing but literal styles, or `null`, `false` and `undefined`, compiles to one constant of its class names and a component that renders nothing, through a new `__n` export, and an import of `css` that no call needs any more is removed.
- A `styled` component whose styles have no rules to insert, as with `extract`, renders no `Styles` beside its element.
- In client builds, a compiled module in which no element can take a `css` prop any more, with none left in place and no JSX spread, compiles its JSX against React's JSX runtime, `/** @jsxImportSource react */`, instead of nishiki's lean one, which would only hand each element on to it.
- A runtime value of a CSS property whose style reaches an element compiles to one static rule per property that reads a custom property, `.n…{color:var(--n-color)}`, and the element sets the custom property inline, so no value adds a rule or rule work at render. This covers a `css` prop on a host element such as `<div>`, the styles of a `styled` component whose element is a tag or a styled component defined at the top of the same module that renders one, and a `css` prop on such a component. A `css()` call, a component the compiler cannot see render an element, a module-level constant, a runtime value under a selector or at-rule key and an object value keep a rule per value as before. Keys still merge per input, the later winning, whether either side is a literal or a runtime value; the element's own `style` keys win over nishiki's custom properties, and the element takes the class only with a value of its own, since custom properties inherit. A CSS-wide keyword such as `inherit`, and a value with `!important`, keep a rule of their own, since in a custom property they would act on it rather than on the property. A value that is invalid for its property now computes as unset rather than falling back to a lower declaration, or as its parent's value where no custom property can hold it either, such as one with an unmatched bracket. `resolve` returns the custom properties as a third element where there are any, `Entry` from `@nishikijs/react/core` carries them as a fourth, and compiled code calls a new `__d` helper with the custom property, the layer of the key and the build's formatter, `__v` or `__f`, for the values it cannot set as one.
- A runtime value that keeps a rule of its own is formatted by a function each module makes once per key. With `extract` it is a new `__f` helper, which takes the hash state, unit and property name the build derived from the key, so the lean runtime an extract build ships leaves out the code that formats declarations and selectors (1,789 B gzipped with every helper, against 1,861 B before); without `extract`, `__v` keeps formatting with the code that unpacks the module's entries. `__v` now takes the key and layer only, so code compiled by an earlier version has to be compiled again.

### Fixes

- A persistent cache no longer replays modules that another build of nishiki compiled. Their code calls that build's runtime, so after an upgrade, or a prerelease, pkg.pr.new or workspace build that changes the compiled output, a cached module could call a helper the new runtime no longer has and fail in the browser or the server, as `d is not a function`. Next.js with Turbopack replayed them in production builds from `.next/cache`. Each cache now keys the modules nishiki compiles on its version and a hash of its code as well as on its options: webpack's, Rspack's and Rsbuild's `cache.version`, Farm's `persistentCache.envs`, the options of the loader Next.js runs under Turbopack, and, for a cache handed to Rollup, `shouldTransformCachedModule`, which also stops Rollup replaying modules compiled with other options. webpack and Rspack no longer list nishiki's code as a build dependency, which the version replaces. A hand-written Turbopack rule for `@nishikijs/react/unplugin/loader` does not change with nishiki, so delete `cache` and `dev/cache` in the Next.js output directory (`.next` unless `distDir` says otherwise) whenever nishiki's code changes, or use `withNishiki` from `@nishikijs/react/unplugin/next`.
- The loader that Next.js runs under Turbopack no longer compiles nishiki's own files when a workspace links the package outside `node_modules`, where Turbopack does not count it as foreign. It read the runtime's `css` props as styles left to the runtime, as the build plugin already knew not to.
- The compiler evaluates every runtime value of a style object in written order, also one that a later literal key overrides, so its expression still runs and a later value that depends on it sees the same result as without the compiler. An overridden value is evaluated for its side effects only and, as in the object literal, never reaches the merge, so its getters are not read.
- A style object with a runtime part keeps the key order JavaScript gives it: the compiler compiles its literal values in place and leaves the object itself to runtime. A literal key that repeats a key of an earlier spread used to move after the spread's other keys, so `{ ...base, "@media (min-width: 600px)": … }` placed the 600px query after `base`'s 900px query and let it win where both match; a runtime value written after a literal key used to come out in front of it.
- A computed `["__proto__"]` key compiles as an ordinary key, as in JavaScript, instead of as the prototype of the style object, and a non-computed `__proto__: { … }` stays the prototype in an object with a runtime part.
- A key written twice in one style object compiles as JavaScript builds the object, at its first position with its last value, also when its first occurrence comes before a spread or computed key. `{ ":hover": a, "&:hover": b, ":hover": c }` used to compile to `c` where `css()` gives `b`, and a repeated media query could land after one it should precede.
- An at-rule key with whitespace before the `@`, such as `" @media print, screen"`, compiles as one at-rule instead of a selector list, and keys are trimmed of CSS whitespace only, so a no-break space stays part of a name.
- A backslash escape in a key is kept: `"--a\\,b"` is one custom property instead of a selector list, and an escaped trailing space is no longer trimmed.
- A class name includes the rule's layer, so the same declaration in two layers gets two classes and merging cannot drop one of them. Every class name changes.
- webpack, Rspack and Rsbuild builds with `extract` keep the stylesheets kiln adds to a module when that module's `package.json` declares `"sideEffects": false`. They used to drop them as unused imports, leaving the page without kiln's rules.
- On Windows, the compiler leaves modules under `node_modules` alone. It recognised a dependency only by forward slashes, so on backslash paths it compiled dependencies and gave them `@nishikijs/react/lean`, without checking that they never hand a style object to the runtime, which then had no compiler for it.
- The package declares that it needs Node.js 24 or later in `engines.node`. On an older Node.js, loading the compiler fails with `[nishiki] The compiler requires Node.js 24 or later` instead of `RegExp.escape is not a function`.
- An at-rule key that cannot hold styles, such as `@keyframes`, `@font-face`, `@property`, `@page`, `@counter-style` or `@font-feature-values`, is a type error, and compiling one throws a `[nishiki]` error, from the compiler with the file that uses it. It used to compile silently into CSS that wrapped the element's rule in the at-rule, which browsers drop. Write these at-rules in a plain stylesheet.
